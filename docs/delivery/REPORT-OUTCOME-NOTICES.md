# Report outcomes and complaint guidance

DEFAULT D267 implements117 using the approved D214 support URL/email. Members can complain about report handling or raise Online Dating Code concerns, with an optional existing support reference from Account standing. No new corporate form, ticketing service, SLA, monitored-mailbox guarantee or signatory/compliance claim is introduced. Routine and serious report confirmations, Notices and Account standing offer country-aware Safety & Support and the complaint channels. Offering resources after every report avoids inventing a sexual-misconduct classifier.

## Source decisions and notification privacy

All reports use the same reversible centre-only DEFAULT. New reports establish a silent checkpoint in the source transaction; absent legacy checkpoints establish a silent baseline, never a historical broadcast. Fingerprints contain only actual closure/action/lift/decided-appeal/removal metadata. Internal notes, views, acknowledgements and UpdatedAt do not manufacture outcome notices. Source-specific monotonic revisions preserve a later A→B→A transition without duplicate retry sends.

The actual source decision, checkpoint and generic notification commit atomically under preservation/case authority. A failure rolls them all back, including report creation's optional block. Existing sanction/appeal member notices remain their own approved workflow; external effects occur after the source/outcome transaction. No push/email/SMS or provider dispatch is added for reporter outcome notices.

The centre says only that a report the member submitted has an update and links to existing Notices and reports. It rechecks exact report ownership and current active-account eligibility; malformed actor/mode or absent/foreign source pointers are suppressed. No subject, category, staff reason, evidence or public case identity appears. Barred active members may still read their own general report outcomes. Pending/deleted/absent reporters receive no recreated notification; their checkpoint advances silently and reactivation does not backfill suppressed notices.

General outcome wording stays with the existing ReportPolicy: broad outcome only, never which action or private reasons. A recorded decision change can create a generic update even if the existing broad outcome string remains unchanged. This is not proof the report was upheld, a disclosure of sanctions, or a guarantee of a particular resolution.

## Source retention

Checkpoint foreign keys bind the report, source case and reporting account identity together. Their lifetime is the source report/case lifetime. Ordinary content expiry does not erase still-required minimal report history. Hold-aware case-record expiry deletes report outcome centre rows and their delivery metadata in the same transaction before the report/checkpoint source disappears. A late producer cannot create a checkpoint for a missing source or restart a source retention clock. Account deletion removes the recipient's centre rows; later staff decisions do not recreate them for an inactive account.

Actual commands, failures, results and browser/native limits are in VALIDATION.md. Legal57, actual support operations and verified Code compliance remain separate owner acceptance work.
