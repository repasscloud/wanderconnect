# Staff account and access management — #206

CONFIRMED sources: [#206](https://github.com/repasscloud/wanderconnect/issues/206), [#196](https://github.com/repasscloud/wanderconnect/issues/196), Q131 A ([#192](https://github.com/repasscloud/wanderconnect/issues/192), D324), D189 and D327. This slice follows the Business role draft and precedes #193 MFA management.

## Implemented boundary

Admin → Staff accounts (`/staff`) lists internal accounts with name/verified-email, role and status filters, provider MFA filtering and recorded sign-in date filtering. MFA filtering reads provider credentials, never infers enrolment from roles; narrow searches to at most 200 candidates before applying this remote filter. An unknown provider state is never rendered as disabled. Detail shows provider names/email/phone, verification/enabled state, credential **types**, required actions, open sessions and staff audit history. Tokens, provider session ids, authenticator material and passwords never enter these responses.

`/api/admin/staff/accounts` uses existing Swoovr account and role records. Create provisions a disabled Keycloak user with VERIFY_EMAIL and CONFIGURE_TOTP, commits a locked application account and explicit roles, then confirms provider activation before opening application access. No email ownership is asserted. Multiple internal roles are supported. Business Partner/member/venue roles cannot be submitted as internal roles. The provider and application identities are bound by the returned Keycloak subject, never email lookup.

Updates acquire actor and target lifecycle authority in canonical order, re-read status, roles and session cutoff, enforce recent MFA authentication, compare `StaffRevision`, and close target access before a remote write. Unconfirmed provider effects leave the target locked; retry from its latest revision after reviewing it. Role replacement, revocation of old purpose grants, pending invitation cancellation and audit are transactional. Sign-out advances the conservative existing session cutoff before provider logout; no refresh success can reopen an old sign-in. Account emails remain accepted only through verified token evidence after a provider email change. Staff last-sign-in records admitted token auth_time, separately from LastSeenAt.

Only Root appoints/removes Legal officers. Root itself remains controlled by the existing operator recovery process, and self-management is refused. A staff account in the members realm is never created by a role edit. Legal/Business/T&S/Support have no management endpoint authority without a separately assigned Admin role. All changes wake the existing Zammad synchronizer; its effective queue matrix still excludes Business, and locked/suspended accounts lose mirrored agent access. No new Zammad role mapping is invented.

DEFAULT audit reason input is a bounded machine reason (`staff-onboarding`, `role-change`, `security-review`) or case reference (`case:1234`). It is stored with actor/target/action/time without copying arbitrary identity data into the permanent log. Confirmation checkboxes and compare-and-swap revisions are required. Existing sensitive-access middleware also records refused staff route attempts.

## Credentials and configuration

A separately configured staff-realm service client is required: `StaffAdmin:ClientId` (default `swoovr-api-staff`) and `StaffAdmin:ClientSecret`, restricted to staff-realm `realm-management` view-users/manage-users. It must not be the member or master credential. This task provisions no real identities and changes no runtime/production settings. Provider calls do not retry uncertain writes or follow redirects, and HTTP loggers are removed.

CONFIRMED D32: employees authenticate through Entra. Swoovr must not create a local employee password as a workaround. No password values are accepted, stored or shown by these forms. The adapter supports provider reset email / UPDATE_PASSWORD required action for the existing explicitly enabled Development-only direct-password fixtures; hosted staff receive `password-managed-externally` and use the organisation's Microsoft credential process. Temporary password assignment and clearing corporate credentials remain unavailable because this application does not own them. Root recovery stays operator controlled. #193 adds credential clearing/re-enrolment and session-bound MFA elevation; the #206 branch already requires recent trusted MFA for mutations.

## External partners and acceptance limits

Business is internal. External Business Partner/Organisation Owner membership must be evaluated in the existing separate venue/partner identity boundary, with an authoritative organisation and future organisation-scoped permissions; neither grants an internal role. Organisation creation and the partner portal are explicitly separate work items. There is currently no authoritative organisation catalogue to validate an association, so this slice rejects partner-role input rather than minting unaffiliated accounts or speculative organisation IDs/tables. External partner provisioning is therefore blocked on that separate domain.

Provider activation lost after create may leave a disabled unassociated provider user; the application grants no authority by guessing the user id on retry. Operator reconciliation is required for that rare uncertain-create case. Hosted Entra first-broker linking and field ownership must be verified against the deployed provider before pre-provisioned accounts are used. No hosted acceptance, actual Zammad outage/revocation timing, real email delivery, browser or mobile journey is claimed by portable/fake-provider tests. The generic existing account access and provider boundaries remain fail closed.
