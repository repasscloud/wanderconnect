## Scope and defaults

CONFIRMED D11/D14/D15 remain unchanged. DEFAULT D17 adds host-side Node >=22 tooling using built-in APIs, no npm dependencies or application projects. It registers only `swoovr-investigation`, a public investigation client, with one callback `http://127.0.0.1:8280/callback`, S256 required, implicit/direct grants disabled, no CORS origins, and no application roles. This is neither the future web nor mobile client registration. Static SSR and Q03 remain unchanged.

The client alone binds a copied browser flow `swoovr-investigation-browser-v1`; realm browser defaults stay untouched. The copied username/password execution has reference `swoovr:password`, with an experimental 60-second maximum age. This intentionally short investigation window is NOT the product's privileged-session freshness decision. AMR and broker-note mappers are configured; no social provider is configured. Presence/absence of the broker note does not approve a direct method. A user may have both direct and linked identities; registration history is not inferred.

Provisioning uses the existing private bootstrap credential through local Admin REST. That management password grant does not test browser authentication. An opt-in, privately generated fictional-adult fixture uses an `.invalid` email address. Its email-verified status is **administrator-asserted simulation only**, to allow investigation without SMTP. No ownership, message delivery, adulthood verification or ID/liveness proof is claimed. Fixture password, username and server user ID remain in ignored mode-600 `.local/swoovr-auth-fixture.json`. Keycloak's default user-profile policy drops unmanaged attributes, so they are not used as fixture ownership proof. Existing users must match the private stored user ID; collisions fail closed. Existing clients/flows/configuration require harness ownership markers. No public/development infrastructure deployment is authorized.

## Harness boundary

`./scripts/docker-local.sh auth` listens only on 127.0.0.1:8280. Open that exact address. A host-only HttpOnly, SameSite=Lax cookie binds random five-minute, one-shot state/nonce/PKCE transactions to the browser. POST actions require a server-generated CSRF value and exact same-origin Origin. Host checks prevent alternate hostnames/DNS rebinding; explicit form destinations and same-origin referrers preserve the browser redirect while suppressing cross-origin referrers. Tokens stay in bounded, expiring process memory; restarting clears them. Pages are no-store and reveal only redacted observations. No access/refresh token, password, subject or email is rendered or logged. Standard authorization codes temporarily traverse the provider callback URL; do not copy callback URLs or browser histories into reports.

ID tokens are verified using fixed local realm JWKS, RS256 and a unique matching RSA signing key of at least 2048 bits. Checks require exact issuer, audience/authorized party, nonce, valid numeric times, nonempty subject/session and authentication time. Remote key URLs from token headers are not used. Every observation fetches JWKS again; this is not a rotation acceptance test. Refresh requires the same subject, session and original auth_time. Initial callback nonce is mandatory; refresh may omit it under OIDC 12.2, but a supplied conflicting nonce is rejected. Access tokens are not used or validated against an API. This narrow handwritten investigation verifier is not a production OIDC adapter.

Logout invokes Keycloak's token logout endpoint server-side, then requires actual HTTP 400 `invalid_grant` to report refresh rejection. Network failure is not evidence of revocation. Browser cookie removal, front/back-channel application logout, concurrent refresh races and revocation of already-issued access tokens remain separate gates. Privileged access is always disabled, including when password AMR is present. No adapter populates the Domain verdict.

## Reproduce

1. Run `./scripts/docker-local.sh init` and `./scripts/docker-local.sh up`.
2. Run `./scripts/docker-local.sh auth-init`; repeat to check idempotency. This updates the existing imported realm through Admin REST, so no volume deletion/import reset is needed.
3. Run `node scripts/auth/provider-check.mjs` for actual provider rejection checks (redirect, missing/plain PKCE and password grant).
4. Run `./scripts/docker-local.sh auth`; open `http://127.0.0.1:8280/` in a normal browser. Read the private fixture locally for manual sign-in; never paste it into chat, reports or shell commands/history. Do not save its password in your browser.
5. Log in with the fixture. Inspect validated ID-token and password-AMR observations. Refresh and probe silent SSO: original authentication time/session should remain unchanged. Wait more than 60 seconds, then refresh: password AMR should disappear, despite a valid session and newly issued ID token. Force password reauthentication and enter the fixture password: observe a fresh authentication time and restored AMR.
6. End the provider session: the report must show refresh rejected. Run `./scripts/check.sh` for offline tests and portable application checks.
7. Stop the harness with Ctrl-C and containers with `./scripts/docker-local.sh down`. Local fixture files and volumes are retained. When deliberately replacing a disposable realm/volume, preserve or move the matching private fixture file too; a stale user ID must not be silently adopted. Interrupted creation before ID recording fails closed and requires inspecting the disposable fixture, not relaxing ownership checks.

Do not run `docker compose config`, print environment files, export users/credentials, or publish raw browser traces for evidence. Existing local reset instructions apply; no destructive reset is needed for ordinary reruns. See [actual validation](VALIDATION.md).

## Session consistency follow-up — 16 October 2026

DEFAULT D18 tightens the investigation boundary: each browser begin supersedes earlier unfinished callbacks; one provider operation per local session may run at a time (overlaps return 409); logout invalidates pending callbacks. Silent SSO must retain any previously observed subject, session and original auth_time. Forced reauthentication must retain an existing subject and return auth_time no earlier than transaction creation minus five seconds of clock tolerance; a new provider session is allowed. This tolerance validates the requested experiment, not product privileged freshness. Explicit ordinary browser login can switch identities.

These are local harness assertions, not a production OIDC adapter. [OIDC ID-token validation](https://openid.net/specs/openid-connect-core-1_0.html#IDTokenValidation) requires checking requested authentication age; the harness now checks the forced reauthentication result rather than merely sending max_age. Signed synthetic JWKS rollover/removal cases exercise verifier behavior, not actual Keycloak rotation. No provider roles, email ownership, social transitions or application grants are added.
