# Neutral conversation endings and support

CONFIRMED requirements D213/Q85 and D214/Q86; implementation DEFAULTs D223–D225. Sources: [owner requirements](OWNER-DECISIONS-2026-10-29.md), issues [110](https://github.com/repasscloud/wanderconnect/issues/110) and [111](https://github.com/repasscloud/wanderconnect/issues/111).

Ending retains read-only history, disconnects every currently connected mode, keeps D176 eligibility rules and never automatically blocks/reports/penalises anyone. The exact three fixed farewells (or none) precede the neutral System event. The ender sees the owner's first-person text; the recipient sees the neutral text. System/farewell events cannot be deleted for both. Closed history can still be hidden personally, reported or blocked. New connections create a new conversation.

The internal initiating id stays in restricted provenance/audit, never public event metadata; exports label system events as system. Message-report eligibility rejects System for both members, preventing an indirect initiating-party inference. Conversation reports remain available; internal evidence labels system messages clearly. Web and app preserve history when the live closed event arrives. Upload responses cannot overwrite a newer live photo-screening/deletion event. Chat screening is queued after the upload transaction commits, preventing the worker from consuming an invisible row. The screen follows Swoovr's existing tokens and the neutral supplied HTML reference; docs/design remains read-only.

The recipient centre/outbox item is in the same transaction. Dispatch is deduplicated by closure/recipient and journals device intent/outcome before moving to another device. Uncertain acceptance is recorded as unknown without blind resend. The startup/periodic API worker and `notifications sweep` resume incomplete items. Generic closure push text never includes farewell/private previews. Existing actor, block, sanction, preference, mute and quiet-hour rules remain enforced; in-app centre is independent of remote push. This is not a physical delivery guarantee. PostgreSQL locking semantics were checked against the [PostgreSQL 17 advisory-lock reference](https://www.postgresql.org/docs/17/functions-admin.html#FUNCTIONS-ADVISORY-LOCKS).

Standing (web, app, admin) and draft privacy show https://swoovr.com/support and support@swoovr.com. A report-specific support link passes its reference, not report content. No corporate form, ticket routing, mailbox operation or SLA is built or verified here. Privacy notice stays DRAFT (issue 57).

Validation and limitations are recorded in [VALIDATION.md](VALIDATION.md). No merge, deployment, Actions activation, provider credentials or physical-device delivery is authorised by this slice. Blocked-photo interruption recovery remains separate issue 126.
