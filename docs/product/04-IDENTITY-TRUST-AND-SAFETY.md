### Email links and sessions

Magic links return to the intended web/app destination and exchange a short-lived, single-use opaque token for a session. Do not place long-lived access/refresh tokens in URLs. Bind the request to the audience and intended client/session; use an allowlist of callback destinations, verified universal/app links on mobile and an explicit cross-device recovery path. Finalize on a user-confirmed POST/exchange so email scanners cannot consume a sign-in simply by fetching the link. Atomically reject replay, expiry and wrong-audience tokens; use generic responses, resend throttling and rate limits. Never log link tokens or leak them via referrers/analytics. Token lifetime, delivery service and Keycloak support are integration questions in [the backlog](../delivery/QUESTIONS.md).

Use supported standards-based flows where Keycloak actually provides them: OIDC authorization code + PKCE, state/nonce validation and system browser on mobile are the target design, pending contract verification. Validate issuer, audience, signature and expiry server-side; bind identity to issuer/subject. Do not merge accounts by matching email strings. Linking/unlinking requires reauthentication and safeguards against losing the last login method; a social-authenticated session must never gain privileged access through account linking. Staff accounts may hold social links, but a social-authenticated session cannot access privileged areas. Handle Apple private relay addresses and provider revocation.

Website DEFAULT: backend-for-frontend session using Secure/HttpOnly cookies and CSRF protection. Mobile: secure OS token storage, rotation/revocation, session list and remote logout. Native apps never contain provider client secrets. No live login is implemented by the foundation scaffold; provider integration fails closed until verified. See [authentication architecture](../architecture/AUTHENTICATION.md).

## 3. Images and account abuse

On upload: validate MIME by decoding, size and dimensions; strip unnecessary metadata; malware/unsafe-content checks; private object storage; SHA-256 of original bytes; hash normalised pixel representation for exact decoded matches; perceptual hash for candidate similarity; compare across accounts and enqueue meaningful matches. Hashes do not prove image ownership or impersonation. Never expose matched account identities to an uploader. Group photos, stock images and legitimate re-created accounts require interpretation. Perceptual hashes can have false positives/negatives; thresholds require validation. Avoid face-recognition identity clustering in the prototype.

Combine with rate limits, repetitive-message/link patterns, device/session risk and user reports. No automated permanent ban solely from image reuse or raw negative feedback. Staff review must include reason, evidence, action and appeal path. Define limited retention for fraud evidence and deletion/tombstone hashes rather than retaining an unlimited hidden library.

An approved ID check marks the profile's date of birth verified only when the document's date matches (D158); otherwise the member gets one correction, checked against Didit again, and a remaining mismatch goes to an admin's manual review while ID Verified stays (D166). Separate private chemistry feedback from reports. Handle urgent threats and suspected minors through appropriate documented escalation processes. No public rating of attractiveness. No coercive sexual solicitation, paid sexual services or exploitation. Casual intent must not be silently removed from requirements, but public content, messaging rules and app-store positioning need explicit policy assessment before launch.

Access exact location only for necessary eligibility; expose coarse areas. Exclude private profiles/media from public indexing. Authorise every media request using revocable access controls; expiring signed URLs have revocation limitations and require short lifetimes or a mediated delivery layer where needed. No claim screenshot prevention is reliable.

Collect consent and purpose for sensitive information; restrict staff access; encrypt transit/storage; audit privileged reads; define deletion/export and retention schedules with professional review for launch markets. Account deletion must revoke access and explain legally necessary retention and subscription management. Do not assume deleting an account automatically cancels an Apple/Google subscription. Avoid sensitive analytics payloads and revealing lock-screen notification previews by default.
