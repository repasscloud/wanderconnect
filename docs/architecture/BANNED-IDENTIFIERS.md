# Banned identifiers

CONFIRMED D217 / issue118, approval in principle subject to legal57. Status: registry foundation and API admission/contact-change enforcement. Registry population/backfill, staff workflows, member/admin UI, necessity reviews and registry-history disposal remain in the next slices. This is not end-to-end ban-prevention readiness or a claim of Code compliance.

`BannedIdentifier` extends existing case/enforcement infrastructure. It stores the identifier type, a32-byte HMAC-SHA256 fingerprint, positive key version, case reference, standard reason code, status, UTC timestamps and match counters. It has no plaintext email/mobile or secret key field. A case relationship restricts deletion rather than cascading enforcement records when ordinary member data expires. Integration must keep only necessary case/account provenance while original evidence expires independently.

Email uses existing trim/invariant-case normalization without provider-specific dot or plus-tag rewriting. Mobile uses existing E.164 normalization. Fingerprints use separate `email` and `mobile` purpose labels, so type separation is cryptographic as well as part of the database query. Matching must check type, key version, hash, Active status and `(BanExpiresAt == null || BanExpiresAt > now)` in the query; it must not wait for a worker to mark expiry. A missing historical key must make matching unavailable, never imply no match.

`Bans:HmacKeys:<positive-version>` is base64 key material of at least32 bytes, supplied by secure server configuration. `Bans:CurrentKeyVersion` optionally pins a configured current key; otherwise the highest configured version issues new fingerprints. Explicit rings replace implicit fallback entirely. Hosted environments have no founder fallback. Development without an explicit ring may derive version1 from founder1 with a separate purpose; adding founder2 cannot alter it. No secret is stored in the database or included in diagnostics. Old fingerprints cannot be rotated without the corresponding identifier; retain required old keys or perform a controlled migration on an authenticated known value. Do not discard an old key merely because a newer current key exists.

Identifier revocation and account reinstatement are separate operations. `BannedIdentifierPolicy.Revoke` requires a staff actor, an active documented restriction and a nonblank bounded explanation. It sets Revoked, expiry/review/revocation timestamps and actor, and constructs matching transition and case-note records. Callers must authorize/conflict-check first and commit all three together. Full before/after snapshots use named enum values; restricted snapshots contain fingerprints, never plaintext identifiers or keys. They must not be relayed to members or generic logs. PostgreSQL rejects ordinary UPDATE, DELETE and TRUNCATE of transition/note history. Authorized scheduled expiry requires a separately bounded disposal authority; ordinary trigger removal is not an operator procedure.

DEFAULT inactive history minimum is24 calendar months from the latest ending/review. Active restrictions have no automatic history-expiry date. Proposed necessity reviews recur every6 months. Legal57 must approve indefinite serious-ban justification and inactive-record disposal before unrestricted beta. These domain clocks alone do not implement jobs or prove legal compliance.

## API admission and contact changes (D237–D239)

The API now checks actual registry rows before first verified-email application registration and before adopting a different verified email. Registration serializes by authenticated issuer/subject, takes a preallocated account-state lease and then shared preservation authority. A single transaction commits account, profile and any required legacy-review case. Quota attempts commit first; failure cannot erase the rate record or leave a partial new member. Existing profile creation has the same profile/case transaction boundary, and its insert-race handler does not swallow a later case failure.

A different Keycloak email that matches an active restriction is rejected before application email/contact-history changes. The legitimate account is not banned or silently assigned another address. An existing still-valid legitimate session remains usable. **Boundary:** Keycloak owns authentication; it may already have created or changed its user record. The API blocks application registration/adoption, not the Keycloak form. Member recovery/error UI remains integration work; no Keycloak form-level rejection is claimed. Never describe this as rejecting Keycloak user creation. With only a token carrying the refused changed email, the current resolver refuses application calls until the Keycloak email is corrected or the restriction is reviewed. Standing is unchanged, but this is a known recovery gate. Before UAT, the provider/member flow must prevent a refused email change from trapping an otherwise legitimate member; the existing-token test alone does not prove that requirement end to end.

Mobile start checks before creating a challenge; confirmation rechecks after code validation and before attaching/replacing the verified number. Refusal leaves the previous verified number and account standing intact. Shared preservation authority spans the check and application commit. External mail/SMS effects do not hold the global barrier. These paths remain compatible with the existing explicitly simulated local sender; no delivery evidence follows from a successful fixture.

Missing any key version needed by an active unexpired restriction of the requested type returns503 `identifier-check-unavailable`. Expired/inactive rows do not need matching keys. Positive matches return403 `identifier-restricted` with the owner-approved email/mobile wording. Responses are no-store and contain no case, registry ID, fingerprint, source account or original reason.

Quotas are20 per authenticated caller/type and1000 per source address per sliding hour. Caller and address fingerprints use separate HMAC purposes and are distinct from banned-identifier fingerprints. Quota records hold only opaque hashes, key version, type, time, optional known application account and matched registry IDs. Per-caller/address advisory mutexes are acquired after preservation in stable order, across API replicas. Excess calls receive429 and Retry-After; no queried identifier is retained in quota metadata. Source addresses use the existing trusted-proxy policy; hosted proxy configuration is still part of UAT readiness.

Stage a new HMAC key on **all** replicas with the old current version pinned before switching the current version. All replicas must be able to count historical-version attempts and enforce active restrictions. Do not remove old keys while active fingerprints, held quota rows, required history or retained backups need them. A newer current key does not transform old fingerprints into new ones. The tests prove coexistence/matching, not a plaintext-free migration.

Hourly retention expires quota rows older than24 hours, protecting known held accounts and matched cases. Unknown preservation availability/membership stops expiry. These operational rows are not the primary evidence store; review use requires independent preservation. The case-record purge keeps referenced case metadata while registry/history exists; detailed review content continues its own clock. Further case/tombstone minimisation and bounded immutable-history expiry remain required.

The remaining D217 work is still mandatory: populate registry rows from real termination/legacy provenance, authorized independent review/release and explicit account reinstatement reconciliation, necessity reviews, full member/admin UI and inactive-history disposal. The isolated API fixtures seed restrictions directly and do not prove those workflows.
