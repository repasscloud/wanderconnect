# Banned identifiers

CONFIRMED D217 / issue118, approval in principle subject to legal57. Status: registry foundation and API admission/contact-change enforcement. Registry population/backfill, staff workflows, member/admin UI, necessity reviews and registry-history disposal remain in the next slices. This is not end-to-end ban-prevention readiness or a claim of Code compliance.

`BannedIdentifier` extends existing case/enforcement infrastructure. It stores the identifier type, a32-byte HMAC-SHA256 fingerprint, positive key version, case reference, standard reason code, status, UTC timestamps and match counters. It has no plaintext email/mobile or secret key field. A case relationship restricts deletion rather than cascading enforcement records when ordinary member data expires. Integration must keep only necessary case/account provenance while original evidence expires independently.

Email uses existing trim/invariant-case normalization without provider-specific dot or plus-tag rewriting. Mobile uses existing E.164 normalization. Fingerprints use separate `email` and `mobile` purpose labels, so type separation is cryptographic as well as part of the database query. Matching must check type, key version, hash, Active status and `(BanExpiresAt == null || BanExpiresAt > now)` in the query; it must not wait for a worker to mark expiry. A missing historical key must make matching unavailable, never imply no match.

`Bans:HmacKeys:<positive-version>` is base64 key material of at least32 bytes, supplied by secure server configuration. `Bans:CurrentKeyVersion` optionally pins a configured current key; otherwise the highest configured version issues new fingerprints. Explicit rings replace implicit fallback entirely. Hosted environments have no founder fallback. Development without an explicit ring may derive version1 from founder1 with a separate purpose; adding founder2 cannot alter it. No secret is stored in the database or included in diagnostics. Old fingerprints cannot be rotated without the corresponding identifier; retain required old keys or perform a controlled migration on an authenticated known value. Do not discard an old key merely because a newer current key exists.

Identifier revocation and account reinstatement are separate operations. `BannedIdentifierPolicy.Revoke` requires a staff actor, an active documented restriction and a nonblank bounded explanation. It sets Revoked, expiry/review/revocation timestamps and actor, and constructs matching transition and case-note records. Callers must authorize/conflict-check first and commit all three together. Full before/after snapshots use named enum values; restricted snapshots contain fingerprints, never plaintext identifiers or keys. They must not be relayed to members or generic logs. PostgreSQL rejects ordinary UPDATE, DELETE and TRUNCATE of transition/note history. Authorized scheduled expiry requires a separately bounded disposal authority; ordinary trigger removal is not an operator procedure.

DEFAULT inactive history minimum is24 calendar months from the latest ending/review. Active restrictions have no automatic history-expiry date. Proposed necessity reviews recur every6 months. Legal57 must approve indefinite serious-ban justification and inactive-record disposal before unrestricted beta. These domain clocks alone do not implement jobs or prove legal compliance.

## API admission and contact changes (D237–D239)

The API now checks actual registry rows before first verified-email application registration and before adopting a different verified email. Registration serializes by authenticated issuer/subject, takes a preallocated account-state lease and then shared preservation authority. A single transaction commits account, profile and any required legacy-review case. Quota attempts commit first; failure cannot erase the rate record or leave a partial new member. Existing profile creation has the same profile/case transaction boundary, and its insert-race handler does not swallow a later case failure.

A different Keycloak email that matches an active restriction is rejected before application email/contact-history changes. The legitimate account is not banned or silently assigned another address. An existing still-valid legitimate session remains usable. **Boundary:** Keycloak owns authentication; it may already have created or changed its user record. The API blocks application registration/adoption, not the Keycloak form. Member recovery/error UI remains integration work; no Keycloak form-level rejection is claimed. Never describe this as rejecting Keycloak user creation. D243–D245 resolve the original whole-account recovery gate: an existing profile with an accepted email retains it and receives a neutral warning while ordinary access continues subject to its existing gates. First application registration remains blocking. The web/native account and standing screens offer approved support and normal reauthentication; no older token is needed to recover. Provider form-level rejection is still not claimed.

Mobile start checks before creating a challenge; confirmation rechecks after code validation and before attaching/replacing the verified number. Refusal leaves the previous verified number and account standing intact. Shared preservation authority spans the check and application commit. External mail/SMS effects do not hold the global barrier. These paths remain compatible with the existing explicitly simulated local sender; no delivery evidence follows from a successful fixture.

Missing any key version needed by an active unexpired restriction of the requested type returns503 `identifier-check-unavailable`. Expired/inactive rows do not need matching keys. Positive matches return403 `identifier-restricted` with the owner-approved email/mobile wording. Responses are no-store and contain no case, registry ID, fingerprint, source account or original reason.

Quotas are20 per authenticated caller/type and1000 per source address per sliding hour. Caller and address fingerprints use separate HMAC purposes and are distinct from banned-identifier fingerprints. Quota records hold only opaque hashes, key version, type, time, optional known application account and matched registry IDs. Per-caller/address advisory mutexes are acquired after preservation in stable order, across API replicas. Excess calls receive429 and Retry-After; no queried identifier is retained in quota metadata. Source addresses use the existing trusted-proxy policy; hosted proxy configuration is still part of UAT readiness.

Stage a new HMAC key on **all** replicas with the old current version pinned before switching the current version. All replicas must be able to count historical-version attempts and enforce active restrictions. Do not remove old keys while active fingerprints, held quota rows, required history or retained backups need them. A newer current key does not transform old fingerprints into new ones. The tests prove coexistence/matching, not a plaintext-free migration.

Hourly retention expires quota rows older than24 hours, protecting known held accounts and matched cases. Unknown preservation availability/membership stops expiry. These operational rows are not the primary evidence store; review use requires independent preservation. The case-record purge keeps referenced case metadata while registry/history exists; detailed review content continues its own clock. Further case/tombstone minimisation and bounded immutable-history expiry remain required.

The remaining D217 work is still mandatory: populate registry rows from real termination/legacy provenance, authorized independent review/release and explicit account reinstatement reconciliation, necessity reviews, full member/admin UI and inactive-history disposal. The isolated API fixtures seed restrictions directly and do not prove those workflows.

## Population and restricted staff workflows (D240–D242)

Permanent member termination stages current verified application email/mobile restrictions, a minimal source case where necessary, and immutable creation event/note in the same EF commit as the sanction. Only positive account/case provenance qualifies. `dotnet run --project src/Swoovr.Api -- bans backfill` reconciles active sanctions idempotently under exclusive preservation authority; output is counts only and unresolved sources return nonzero. It cannot recover original ownership from legacy unversioned hash-only markers. Final deletion populates attributable terminations before provider effects and retains released entries without recreating legacy restrictions. Existing inactive rows are authoritative, not candidates for automatic reactivation.

Fresh Admin access is required for registry metadata and history. POST `/api/admin/banned-identifiers/lookup` additionally requires `identifier-release` and a purpose; input is never echoed or copied to generic audit. GET the collection accepts `caseId`, `due`, `after`; up to200 visible entries are returned, with `Swoovr-Next-Cursor` for continuation. Excluded cases do not starve later entries. GET `/{id}` returns metadata and authorized case-history notes, excluding fingerprint snapshots. POST `/{id}/review` requires `identifier-release`, an active restriction and a necessity explanation; six-month reviews do not reactivate expired/revoked restrictions. POST `/release` requires that capability, explicit IDs and a bounded reason; repeated inactive release changes nothing. Original account sanctions stay in effect.

POST `/api/admin/accounts/{id}/reinstate` requires the separate `account-reinstatement` capability and a reason. Account-state authority precedes exclusive preservation. Only an existing active application account/profile can be reinstated; deleted, deleting or locked accounts are refused. Staff explicitly select every applicable active source-case identifier restriction; unrelated or incomplete selections fail. Active matches from other cases require separate review. Revocations, reinstatement explanation/case notes, termination lifts, outcome notices and audit commit together. Independent restrictions/holds remain. Ordinary lift and appeal-overturn endpoints refuse active terminations; after restricted reinstatement an authorized independent appeal reviewer can record its outcome. All workflows enforce retained personal/reporter conflicts.

Sensitive-access audit surrounds authorization and records401/403/409/500 as well as successful calls, using canonical matched paths and GUID-only resource parameters. No supplied email/mobile, request body or raw URL parameter is a log resource. These APIs still need staff UI. Legacy hash-only handling, immutable-history expiry, operational minimisation and backup/restore remain mandatory before issue118/UAT completion.


Staff procedure: open each selected entry and its associated case before release. Verify the support circumstances sufficiently to justify release (for example reassignment or an incorrect restriction), then record the assessment without copying identity documents or raw contact values into the note. An active elevated grant and typed explanation are authorization/audit controls, not automated proof of current ownership. Never treat a matching fingerprint as proof that the applicant is the previously banned person. Separate account reinstatement requires its own review; releasing a contact is not permission to restore the old account.


## Recoverable refused email adoption (D243–D245)

For an existing member/profile with an accepted verified email, a restricted, throttled or unavailable new email check refuses adoption only. Retain the accepted email for beta/delivery/history, preserve account standing and all independent gates, and return `EmailChangeProblem` through session/me/standing. The value is a neutral code, not an address, match record or case. Warning responses are no-store. Unknown/profileless/identifierless accounts do not get this continuation path. First registration still returns the approved identifier refusal without a partial member.

`Account.EmailAcceptedAt` is an internal acceptance watermark, not a claim that legacy acceptance happened at that instant. Registration and null→email/changed adoption store max(server time, valid accepted token iat); malformed/unknown issuance uses the conservative five-second skew boundary. A differing token email needs iat newer than that watermark and the latest contact-history change. The initial acceptance clock prevents newest-first pre-registration token replay; retaining accepted future iat prevents rollback within tolerated issuer skew. Replacement requires contact-history keys. The additive migration pins existing nonnull addresses to migration time plus5 seconds, leaving null emails without an invented acceptance. Legacy writers' missing clocks are frozen once. Existing same-email use is unaffected; ambiguous differing claims require fresh sign-in. Final deletion removes the clock with the email.

The member can continue using existing access, contact Support or reauthenticate after provider correction/review. Correcting Keycloak to the already accepted address clears the warning without quota admission or an old token. A different permitted address is adopted when matching/quotas and fresh evidence allow, with the usual protected history/previous-address notification. Do not claim that this restores a suspended/terminated account or changes a legal hold. Staff registry UI, hash-only legacy migration, bounded immutable/operational-history disposal and backups/restore remain required under118.


### Associated case review (D246 / issue130)

Opening the associated case must not bypass a registry conflict refusal. Case detail checks known subject/reporters against the same retained explicit staff associations. Queue and appeal queries exclude conflicted records before their result limit. Detail materialises participant-authorized evidence while holding exclusive preservation authority against ordinary report writes, and returns only sanctions recorded for that selected case. An unrelated sibling case cannot relay a refused case's sanction/reason/ID. Case and appeal reads/refusals add content-free sensitive-access metadata. This does not change ordinary account-summary or every administrative read surface; do not claim blanket administrative privacy from this slice. Staff registry UI is still separate work.
