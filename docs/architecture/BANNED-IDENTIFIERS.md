# Banned identifiers

CONFIRMED D217 / issue118, approval in principle subject to legal57. Status: registry foundation and API admission/contact-change enforcement. Registry population/backfill, staff workflows, member/admin UI, necessity reviews and registry-history disposal remain in the next slices. This is not end-to-end ban-prevention readiness or a claim of Code compliance.

`BannedIdentifier` extends existing case/enforcement infrastructure. It stores the identifier type, a32-byte HMAC-SHA256 fingerprint, positive key version, case reference, standard reason code, status, UTC timestamps and match counters. It has no plaintext email/mobile or secret key field. A case relationship restricts deletion rather than cascading enforcement records when ordinary member data expires. Integration must keep only necessary case/account provenance while original evidence expires independently.

Email uses existing trim/invariant-case normalization without provider-specific dot or plus-tag rewriting. Mobile uses existing E.164 normalization. Fingerprints use separate `email` and `mobile` purpose labels, so type separation is cryptographic as well as part of the database query. Matching must check type, key version, hash, Active status and `(BanExpiresAt == null || BanExpiresAt > now)` in the query; it must not wait for a worker to mark expiry. A missing historical key must make matching unavailable, never imply no match.

`Bans:HmacKeys:<positive-version>` is base64 key material of at least32 bytes, supplied by secure server configuration. `Bans:CurrentKeyVersion` optionally pins a configured current key; otherwise the highest configured version issues new fingerprints. Explicit rings replace implicit fallback entirely. Hosted environments have no founder fallback. Development without an explicit ring may derive version1 from founder1 with a separate purpose; adding founder2 cannot alter it. No secret is stored in the database or included in diagnostics. Old fingerprints cannot be rotated without the corresponding identifier; retain required old keys or perform a controlled migration on an authenticated known value. Do not discard an old key merely because a newer current key exists.

Identifier revocation and account reinstatement are separate operations. `BannedIdentifierPolicy.Revoke` requires a staff actor, an active documented restriction and a nonblank bounded explanation. It sets Revoked, expiry/review/revocation timestamps and actor, and constructs matching transition and case-note records. Callers must authorize/conflict-check first and commit all three together. Full before/after snapshots use named enum values; restricted snapshots contain fingerprints, never plaintext identifiers or keys. They must not be relayed to members or generic logs. PostgreSQL rejects ordinary UPDATE, DELETE and TRUNCATE of transition/note history. Authorized scheduled expiry requires a separately bounded disposal authority; ordinary trigger removal is not an operator procedure.

DEFAULT inactive history minimum is24 calendar months from the latest ending/review. Active restrictions have no automatic history-expiry date. Proposed necessity reviews recur every6 months. Legal57 must approve indefinite serious-ban justification and inactive-record disposal before unrestricted beta. These domain clocks alone do not implement jobs or prove legal compliance.

Follow-up integration must address first application registration, Keycloak email-update boundaries, phone start/confirmation, termination/appeals/reinstatement, historical-key availability, concurrency and hold-aware retention before this migration is part of a ready-to-deploy UAT package.

## API admission and contact changes (D237–D239)

The API now checks actual registry rows before first verified-email application registration and before adopting a different verified email. Existing profile creation has the same profile/case transaction boundary, and its insert-race handler does not swallow a later case failure.

A different Keycloak email that matches an active restriction is rejected before application email/contact-history changes. The legitimate account is not banned or silently assigned another address. The API blocks application registration/adoption, not the Keycloak form. Member recovery/error UI remains integration work; no Keycloak form-level rejection is claimed. Provider form-level rejection is still not claimed.

Refusal leaves the previous verified number and account standing intact. Shared preservation authority spans the check and application commit. Do not remove old keys while active fingerprints, held quota rows, required history or retained backups need them. A newer current key does not transform old fingerprints into new ones. The tests prove coexistence/matching, not a plaintext-free migration.

These operational rows are not the primary evidence store; review use requires independent preservation. The case-record purge keeps referenced case metadata while registry/history exists; detailed review content continues its own clock. Further case/tombstone minimisation and bounded immutable-history expiry remain required.

Verify the support circumstances sufficiently to justify release (for example reassignment or an incorrect restriction), then record the assessment without copying identity documents or raw contact values into the note. Never treat a matching fingerprint as proof that the applicant is the previously banned person. ### Bounded inactive history and continuity (D251–D253)

`RegistryDisposal`, coordinated by hourly/one-shot `retention purge`, checks trustworthy hold availability and acquires exclusive authority before current source checks. Inactive history must be at least24 calendar months beyond its latest effective end/review/non-expiry event or note; a late system-expiry processing event does not renew this minimum. Independent case record windows include closure, escalation/referral, appeal/export/disclosure and explicit reinstatement reviews. Unknown membership/status/source, pending appeal/open case or retained related copies fails closed.

A transaction inserts a nonmatchable `BanDisposition`, deletes associated note text and snapshot/events, then the fingerprint row. Database predicates independently require current eligibility and matching creation/terminal/note provenance. Statement triggers acquire the database barrier before row work; normal writes share it, destructive/receipt work takes exclusive authority. Row guards then use [fresh VOLATILE reads](https://www.postgresql.org/docs/17/xfunc-volatility.html). Destructive operations reject retained isolation snapshots (anything other than ReadCommitted). Ordinary rewrite/TRUNCATE remain refused, and no global trigger disabling or writable disposal flag exists. Schema owners can alter their database; these controls do not claim to prevent that privilege.

Receipts retain source ID/case/type/inactive end/history/disposal dates, no HMAC, key version, contact or copied reason. Existing termination keeps minimal provenance; backfill and final deletion recognize the receipt rather than reconstruct a restriction from surviving contacts. Separate authorized reinstatement recognizes the disposition, reconciles any still-active identifiers, and adds a new immutable `BanDispositionReview` as the associated case note/event. Its timestamp independently extends retention; original closure remains unchanged. Fresh restricted preview shows receipts/reviews even after termination lift, with no re-enabled action. When original enforcement and every obligation end, the job disposes review/receipt records and existing case/tombstone jobs can finish on the next pass. No deleted account is resurrected.

## Reviewed active mobile binding retirement (D249 CONFIRMED; D254 DEFAULT)

`POST /api/admin/banned-identifiers/{id}/retire-mobile` is separate from restriction release and account reinstatement. It requires admin, fresh authentication, identifier-release elevation, participant-conflict clearance, explicit circumstances/ownership-review confirmation and bounded reason. The API derives the original member from positive associated-case provenance; it never accepts a destination account or transfers ownership. Only a staff-revoked Mobile restriction with a still-active source termination is eligible; automatic expiry alone does not authorize retirement. The current verified number must match the original typed/versioned HMAC. Any other active match requires independent review; unavailable historical keys refuse.

Lock original account lifecycle before exclusive preservation and recheck authorization/source/binding. Sign out that original Keycloak subject before freeing its unique phone binding; uncertain provider outcomes retain the binding. Archive the verified prior number with its original verification time through existing encrypted restricted contact history, requiring archival keys, then atomically remove only `MemberPhone` and append `mobile-binding-retired` transition/associated case note. The new review extends the original registry-history clock without changing revocation or account sanctions. Rollback after remote logout leaves a safe retry; no compensating sign-in is minted. A recorded completion returns unchanged only with no current phone; it cannot remove any later binding.

No SMS is sent to the recycled number. Original email, other provider credentials, ban and lawful history remain; a new owner must complete ordinary verification before attaching the freed number. Existing legal-hold retention applies to the encrypted archive. Recovery of the original account is separately reviewed. This implements mobile only: provider email/login retirement must also prevent mailbox recovery and linked-provider reintroduction before being exposed.

D254 also records a monotonic `SessionsRevokedAt` watermark atomically with retirement: old self-contained JWTs remain refused after any later independent reinstatement. New authentication must be later than the cutoff; Keycloak auth_time has whole-second resolution. The integrated regression checks note-failure rollback of this watermark, old-token refusal before/after separately reviewed recovery and a fresh sign-in using preserved credentials.

Revocation clock DEFAULT: the retiring original subject's cutoff includes the shared30-second admitted issuer skew, so a recently issued token from an issuer ahead of the API cannot survive retirement. Revoked-account acceptance requires both authenticated-at and issued-at later than the cutoff; missing/invalid/excessively future issuance fails closed. Original-account recovery sign-in may need to wait through that brief cutoff. This does not delay the legitimate new owner's registration/verification. Exact skew and malformed-clock cases are deterministic policy evidence; no real Keycloak clock shift is claimed.

## Durable email intent (D257 DEFAULT)

The restricted API prepares retirement only for an explicitly revoked email restriction with positive active source termination, matching current accepted/provider email, trusted issuer and fresh/elevated conflict-free review. The transaction saves cleared/retired source state before inserting the command so the database source guard sees it; both remain invisible until that transaction commits. The encrypted envelope uses existing contact-history keys and binds source/operation/case/registry/issuer plus exact provider CAS fields. No plaintext contact or provider diagnostics enter generic audits.

Pending/NeedsReview blocks original API resolution, while the retired-contact flag separately prevents later claim adoption. Background work rechecks original grant/current role, source case and termination, all matching restrictions and related conflicts under lifecycle/preservation authority before new remote effects. Missing receipts do not establish no effect. A confirmed current provider receipt can reconcile a previously committed effect even after grant revocation; it atomically refreshes the token cutoff and marks completion. Partial failures keep durable intent. Disabled configuration makes no request or invented outcome.

Command records have source/case restrictive foreign keys and guarded immutable provenance/completion. They participate in the contact-history key set. Completed records expire only after24 calendar months and the database's current case/hold predicate; pending uncertainty is retained for restricted review. Keyset sweeps pass retained prefixes. Source email/contact recovery is independent of account reinstatement; the unfinished staff resume/recovery workflow must not automatically transfer an original subject to a recycled mailbox. The backend remains off by default pending that integration and application/provider journey proof.
